## 1. 背景与目标

### 1.1 业务背景与痛点

**业务背景**

在招投标领域，工作人员在标前审查阶段需要对投标公司进行资质核查，包括违法失信记录、异常经营状态等信息。核查结果需以截图形式留档，作为评审依据。查询方式为：在目标专业网站的搜索框中输入投标公司的完整名称，系统返回查询结果页。

**当前工作流程**

```
准备公司名单
    ↓
打开第一个目标网站
    ↓
逐一输入公司全称 → 等待结果加载 → 手动截图 → 本地重命名保存
    ↓
切换到下一个网站，对所有公司重复以上操作
    ↓
全部完成，整理截图文件
```

**现状痛点**

| # | 痛点 | 影响 |
| --- | --- | --- |
| 1 | 全程人工操作，无自动化辅助 | 单次任务耗时长，人力成本高 |
| 2 | 同一家公司须在多个网站逐一查询 | 重复操作多，出错与遗漏风险高 |
| 3 | 网站偶发超时，流程被动阻塞 | 不知是否遗漏，需从头检查 |
| 4 | 无任务进度追踪与断点记录 | 中断后难以判断查到哪里，只能重跑 |


### 1.2 产品目标

> 只通过输入N个公司名称，选择想要截图的网站，即可全自动完成多个网站的截图任务，无需人工再介入。




### 1.3 非目标与范围边界

- 本期明确不做什么：
  - 录屏、云端协助（截图内容仅存本地，不外传）
  - 需登录态的功能（如信用中国"下载信用信息报告"），列入后续版本
  - macOS 版本（仅列入后续规划，本期仅 Windows）
  - 截图编辑、标注、选区
- 与其他产品/系统的职责边界：暂无

## 3. 产品形态与体验原则

### 3.1 部署与交付形态

> 桌面应用、浏览器扩展、命令行工具、SDK 库，还是服务端 API？

- 交付形态：独立桌面应用（Windows 安装包，安装后即可使用）
- 平台优先级：Windows（本期）> macOS（后续规划）
- 入口：系统托盘菜单（常驻，提供任务状态与菜单入口）；任务执行时可显示悬浮进度提示
- 界面形态：极简主窗口（任务配置、执行进度、结果摘要），无多余设置项

### 3.2 集成方式

> 是否需要嵌入到其他产品？以什么形式集成（API / SDK / 插件）？

- 目前版本不需要嵌入，只作为独立桌面应用。后续可能会挂到某个平台上，然后下载本应用即可。
- 是否需要登录、账号体系或企业组织绑定：不需要登录、无账号体系；采用 License 激活码方式管控用户授权，规则如下：
  - 激活方式：用户获得激活码，首次启动时输入激活；激活码与当前机器绑定（机器码），换机需重新激活
  - 校验方式：激活后离线本地校验，无需持续联网
  - 有效期：激活码含有效期（建议 1 年），到期前 7 天启动时提醒续期；到期后停止发起新任务，已生成的截图与报告不受影响
  - 激活状态与剩余天数在"设置/关于"界面展示

### 3.3 体验原则

- 默认一次操作完成，避免打断当前工作
- 用户可以在截图期间，正常使用其他应用（截图在独立浏览器实例中执行，不抢占焦点）
- 不采集或上传截图内容，除非用户主动选择
- 本期目标网站均可匿名访问，无需登录；网站账号密码输入为可选配置项（用于 W-006 登录以降低验证码频次），由用户主动填写、仅存本地，不随截图上传

## 6. 核心用户流程

### 6.1 主流程（Happy Path）

```
输入本次查询项目名称->输入N家企业名称-> 选择目标截图网站清单->选择截图文件保存路径->点击执行后，后台运行->系统反馈结果，生成任务成功失败的明细报告文件->将截图和明细报告文件一同存储到指定路径，并项目名称命名zip形式压缩 → 结束。
```



### 6.2 异常与分支流程

- **取消流程**：用户点击"取消"→ 停止发起新任务 → 已完成的截图保留 → 提示「可从上次断点继续或全部重新开始」
- **中断/崩溃恢复**：启动时检测到未完成任务 → 弹出选择框：「从上次中断处继续」/「全部重新开始」
- **单条目失败**：网络超时、验证码未通过、页面结构异常等 → 标记失败并继续下一项，任务结束后汇总至摘要报告（详见第 9 节）
- **全部失败兜底**：若所有条目均失败，仍输出摘要报告，并提示用户检查网络与站点可用性

### 6.3 关键决策点与状态恢复

- 用户在哪些步骤有选择？默认行为是什么？ 用户只在最开始输入企业名称、选择目标网站范围、选择截图保存位置有选择。其中企业名称必填，无默认值；目标网站范围默认全部；截图保存位置默认为桌面。
- 截取、编辑、上传、保存过程中可否取消？取消后数据如何处理？用户在点击开始执行后，可以主动取消；取消后保留已生成的截图与断点记录，再次启动时可选「从上次中断截图处继续」（已完成 公司×网站 项跳过，不重复执行）或「全部重新开始」（清空本次任务已生成文件后重跑）。
- 应用崩溃或系统重启后，未完成编辑是否恢复？系统崩溃重启后，应让用户选择是从上次中断位置继续还是全部重新开始；断点状态以本地任务文件持久化，随执行过程实时保存，不依赖手动保存。
- 文件冲突规则：单个截图文件名含时间戳；重跑同一项时覆盖旧文件；公司重名时公司文件夹自动加序号后缀（见 7.3）。

## 附录 D：验证码自动处理策略

> 对应 Q-004 结论。策略方向：优先自动识别，失败则自动跳过并记录，全程无需人工干预。

### D.1 策略总览

| 步骤 | 行为 |
| --- | --- |
| 1. 检测验证码 | 页面加载后判断是否出现验证码元素 |
| 2. 自动识别并提交 | 根据验证码类型选择对应方案（见 D.2）尝试自动通过 |
| 3. 验证结果判断 | 识别提交后检测是否通过（页面跳转 / 错误提示） |
| 4. 失败重试 | 最多重试 5次（每次重新获取验证码图片再识别） |
| 5. 仍失败则跳过 | 标记该条目为"验证码未通过，已跳过"，写入摘要报告，继续下一条 |

### D.2 各验证码类型对应方案

| 验证码类型 | 目标网站 | 推荐方案 | 库/工具 | 说明 |
| --- | --- | --- | --- | --- |
| 图形字符（数字+字母） | W-006 gsxt.gov.cn（主要） | 本地 OCR 识别 | [`ddddocr`](https://pypi.org/project/ddddocr/)（开源，离线，无需 API Key） | 支持中英数混合验证码，识别速度快，无网络依赖；识别成功率约 85–90% |
| 滑块拼图 | W-006 gsxt.gov.cn（历史版本有滑块） | 滑块缺口定位 + 模拟拖拽 | [`captcha-recognizer`](https://pypi.org/project/captcha-recognizer/)（深度学习缺口检测）+ Playwright 拖拽 | 定位缺口坐标后用 Playwright 模拟人类拖拽轨迹（带加速/减速）通过极验类滑块 |

### D.4 技术风险说明

- **gsxt.gov.cn 验证码会升级**：政府网站可能随时更换验证码机制，`ddddocr` 的通用模型对新型扭曲/干扰图形成功率下降，需在上线后持续监控跳过率。
- **反爬检测**：频繁请求可能触发 IP 限流。需求层面已固定：默认串行执行 + 请求间随机延迟 1～3 秒（见第 10 节），不提供并行配置；上线后持续监控跳过率与限流情况。
- **降级兜底**：所有自动识别方案均以"失败则跳过+记录"为最终兜底，保证批次任务不因单个验证码卡死。
